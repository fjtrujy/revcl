## Exactly why 186 bytes is still not 185 for Enter

Under `-O2 -frename-registers -falign-jumps=8 -falign-loops=1 -falign-labels=1`, the Jan25 and Dec06 compilers both reproduce the original **five-byte** control-flow alignment at original offsets `+0x2b..+0x2f`, the original allocation branch at `+0x30`, original register assignments, hash calculation and bucket stores up through `+0xa6`.

The compiler emits *another* `.align 8` directive before the C++ exception cleanup handler `.L50`. Since the preceding unconditional branch finishes at `+0xa7`, this produces an extra one-byte NOP at `+0xa7` and shifts the handler to `+0xa8`. The original exception handler starts at **`+0xa7`** without that second NOP, and `Enter` ends at 185 bytes. This is a compiler EH basic-block target-alignment discrepancy, not a mysterious missing hash-table instruction.

The assembly file from the Jan25 snapshot under `/tmp/vuc-binutils215/enter-targeted-align-oct15l.s` contains both GCC-emitted `.align 8` directives. No one has patched assembler output or NOP bytes into a candidate.

Reproducible new experiments:
- `vuc/probes/evaluate_symbol_enter_exception_landing_oct15m.py`: fixed genuine nested-node source, six historically motivated EH scheduling/block-status variants, independently under **both** recovered GCC snapshots. The `-fno-reorder-blocks` variant does emit **185 bytes with five original relocations**, but only **38/185 original-offset bytes** match because reordering the main control flow destroys the otherwise correct allocation branch sequence. This is **not** an acceptable partial or a new exact match. Other variants emit 186 bytes (or 161 with severely altered branch layout).
- `vuc/probes/evaluate_symbol_enter_guard_controlflow_oct15m.py`: normal C++03 empty-vector guard statements (`size()==0`, `begin()==end()`, negated guard, `else`, and `goto` forms) under the instruction-evidenced original eight-byte jump target alignment and both snapshots. All valid straightforward forms retain **186** instead of **185** bytes. One `goto` crosses a C++ object initializer and fails compilation, correctly rejected; no byte padding was used.

All generated C++03, ELF32 compiler objects and JSON score ledgers remain under `/tmp/vuc-binutils215/enter-exception-landing-oct15m/` and `/tmp/vuc-binutils215/symbol-enter-guard-flow-oct15m/` in the existing Lima guest.

### Pinpointing the remaining reserve mismatch

Original `Scope::reserve` at `0x0804ec50` takes its normal return at relative `+0x2e..+0x35` and immediately starts the allocation body at `+0x36`, with **no two-byte branch-target alignment**. It inserts a two-byte NOP `mov %esi,%esi` at relative `+0x6e` before the cleanup loop starts at `+0x70`.

The Jan25 candidate instead emits the two-byte NOP at relative `+0x36` and starts the body at `+0x38`. Its cleanup loop arrives at `+0x70` without a preceding NOP. The original bytes from that point onward coincide again, which explains why the **58 mismatches are confined to +45 and +54..+111**. Both code sequences are legitimate GCC block-placement outputs; moving NOPs manually is explicitly forbidden.

`vuc/probes/evaluate_scope_reserve_jump_vs_loop_oct15m.py` is a bounded instruction-led experiment. It compares actual Jump8/Loop8/Loop16 variants to Jumpless/Loop8/Loop16 and Jump2/Jump4 controls under both GCC snapshots, always compiling the real `ScopeVectorLifecycle.cpp` owner with verified literal ranges and relocation mapping. **Only the historically selected Jump8 variants kept the original 241-byte function**, at **183/241**. Lower jump-alignment settings emit 234, 235 or 237 bytes, failing the strict size gate. The original-looking NOP position cannot be obtained by just switching a global alignment flag without destroying another original branch placement.
