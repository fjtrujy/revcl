# ListFile original owner and historical compiler recovery (2026-10-15)

The existing Lima `revcl-oracle` Debian 12 guest failed early boot with `IO-APIC + timer doesn't work` using QEMU `q35`. The non-destructive Lima configuration `.vmOpts.qemu.machine="pc"` with `.vmOpts.qemu.cpuType.x86_64="qemu64"` successfully booted the existing disk; the historical GCC 3.3.3 aliases were restored from the persistent guest cache using `vuc/scripts/restore_cached_toolchain.sh`. The guest's `/tmp` was empty after the reboot, so only reproducible source/config is retained. The repository mount and compiler now work.

Recompiled `ListFile::WriteToFile` under January GCC 3.3.3 and verified the standalone candidate still scores **875/1071 original-offset bytes** at original length, with all 58 original relocations and 3 original literal bytes authenticated. No byte-exact claim.

New experiment `vuc/probes/evaluate_listfile_real_owner_oct15u.py` tests the real `vuc/src/ListFileUnit.cpp` predecessor methods (`Generate`, `PrintLine`, `Print`) in original source order, with `WriteToFile` before or after `GetNumLines`, under both historical compiler snapshots. The generated `.rodata` is six bytes: `3b 20 00 3a 09 00` (`"; "` then `":\t"`), while the standalone candidate has only the latter three bytes. The original `.rodata` string addresses are `0x08072dd0` and `0x08072dd3`. Both combined orders **fail strict literal ownership**: mapping `":\t"` to source offset 0 is wrong, and correcting it to offset 3 leaves the predecessor `"; "` bytes unmapped. This is a strict evidence limitation, not a compiler mismatch to hide with padding. Do not select a combined unit without a complete original string/relocation map. Standalone selected-candidate promotion remains separate from existing interrupted `TryOpenFile` changes.
