# VUC Value arithmetic source-unit exactness after VCL Operand rebase

Date: 2026-10-13. Branch: `vuc`.

## Base revision and transferable finding

Fetched `origin/main` at **`bbe5056`**, which completes the VCL
`Operand.cpp` function at `0x08056a5c`. The new VCL matching note
shows that reordering existing C++ switch arms can influence historical
GCC 3.2.2 peephole2 scratch selection, **but only in genuine source-unit
context**. VUC is compiled with a different GCC 3.3.3 snapshot.

The checkout initially had no modified tracked files and 146 unrelated
untracked paths. Fast-forwarded the local `main` branch, then rebased
**95 VUC commits** cleanly onto it. All pre-existing untracked files were
preserved. The original VUC archive and executable were never modified.

## Newly exact application function

| Original function | Original address | Instruction bytes | Relocations |
| --- | --- | ---: | ---: |
| `Value::operator*(Value const&) const` | `0x0806eb70` | **222/222** | 1 |

The original and authentic relocation target is
`Value::TypeConvert(Value const&, Value const&, Value&, Value&)`
(`0x0806f7d0`). No string literals or initialized-data objects are
emitted by the recovered arithmetic fragment. The exact source is
`vuc/src/ValueArithmeticUnit.cpp`; accepted config:
`vuc/config/value_multiply_exact_oct13.json`.

Compiler: January 25, 2004 GCC 3.3.3 prerelease and GNU as 2.15, using
`-O2 -frename-registers -falign-jumps=1`.

The essential change is a missing **real source-unit predecessor**, not
new arithmetic semantics or register forcing. The original symbol order:

1. `Value::operator+()`, `0x0806e9b0`
2. `Value::operator-()`, `0x0806ea90`
3. `Value::operator*()`, `0x0806eb70`

The earlier `+` then `*` hypothesis matched **219/222**, with ECX
instead of the original EDX in the integer multiplication case at offsets
155, 162 and 164. Inserting the **already independently exact**
`Value::operator-()` before multiplication makes the same multiplication
source match **222/222** under the unchanged compiler flags.

The compact `ValueArithmeticUnit.cpp` consists of genuine, source-level
C++ addition, subtraction, and multiplication definitions (and an
inline-initialized `Value` constructor). Its subtraction also reproduces
**221/221 original bytes**, independently authenticating the predecessor
inside the same compilation unit. Addition remains **partial**: 216
generated bytes versus 219 original under the multiply-exact flags. It
is **not** promoted by this experiment.

A larger `Value.cpp` source unit containing the actual setters,
comparisons and all three arithmetic methods independently produced the
same 222/222 exact multiplication, confirming that no artificial
predecessor or dummy source code is required. No inline assembly,
assembler directives, register constraints, arbitrary padding,
copied instruction bytes, or forged relocation addresses are used.

### Lexical-order robustness

The new `evaluate_value_genuine_minus_predecessor_oct13.py` script
tested **all six lexical orders** for each of the three real case arms
(1, 3 and 4) in each real `+`, `-` and `*` method, while preserving
the actual method definition order. **36/36** configurations with
`-O2 -frename-registers -falign-jumps=1` and the same flags with
`-fno-gcse` independently reproduced the exact **222/222 multiply
and 221/221 subtract** results. Four-byte jump alignment did not
preserve the original multiply length.

Thus the **real predecessor definition** is the observed cause of the
recovered exactness; the VCL lexical-case-order trick is not needed for
this VUC function, and the extra `-fno-gcse` is not part of the accepted
manifest. These facts must not be generalized to other functions or
used to infer original Makefile options.

### Other bounded controls

- `evaluate_value_mul_switch_lexical_oct13.py`: all six multiplication
  case orders, isolated and with the recovered but subtraction-free
  larger source context, remain **219/222**. This independently
  establishes that lexical order alone was insufficient.
- `evaluate_value_plus_lexical_oct13.py`: all six addition case
  orders in isolated and genuine larger contexts remain **172/219**
  in the original-length, four-byte-aligned form.
- `evaluate_accumulatorable_expect_oct13.py`: 27 period-plausible
  `__builtin_expect` assignments across five alignment configurations
  do not improve the best **61/77** original-size
  `IsAccumulatorable()` body. The exact instruction sequence differs
  in compiler-generated alignment NOP placement; no padding was inserted.
- `evaluate_linecomment_landing_align_oct13.py`: 60 historically
  supported jump, label, loop and section configurations for the
  *real* InstructionList source unit leave the best
  `AddLineComment()` at **147/162**, with a branch/exception
  landing-pad alignment discrepancy.
- `evaluate_value_division_genuine_prefix_oct13.py`: all six division
  case orders with the authentic `+`, `-`, `*` predecessors.
  The best remains **174/235** under eight-byte jump alignment.
  The division body and its float reciprocal semantics need further
  original-source reconstruction.

These scripts are retained as explicit negative evidence and do not
modify the strict acceptance manifests for their partial functions.

## Validation and outstanding limitations

Accepted original named function records now total **189/298**,
covering **12,924/12,924** accepted instruction bytes:
**189 EXACT, 12 EXPERIMENTAL, 97 UNRESOLVED**.

The separate initialized-data and BSS gates continue to verify 244
original initialized-data objects (71,536/71,536 bytes) and 12 BSS
symbol declarations. The original linked ELF is **not** yet identical.

The canonical `vuc/config/exact_candidates.json` and diagnostic
`vuc/config/selected_candidates.json` now include the new multiplier
manifest, and the host test counts are updated with a regression test
for the genuine definition order and original relocation.

The accepted `Value::operator-()` remains independently sourced by
`vuc/src/ValueMinus.cpp`; other accepted constructor and startup
functions still have their own exact source fragments. These separate
reconstruction units intentionally provide **function-level** exact
proofs. Their duplicated definitions must be reconciled with the
authentic, unsplit `Value.cpp` compilation and linker emission before
claiming a complete ELF reconstruction.
